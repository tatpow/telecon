# Как помочь Телекону

Спасибо, что хотите помочь. Сейчас проект в основном ведёт один автор.
Можно сообщить о проблеме, предложить улучшение, поправить документацию
или прислать небольшой pull request. Помощь с использованием ИИ тоже
приветствуется.

Ответы и исправления зависят от свободного времени автора; фиксированных
сроков поддержки нет.

## Если что-то не работает

Откройте [сообщение об ошибке](https://github.com/tatpow/telecon/issues/new/choose).
Пожалуйста, укажите:

- версию Телекона, ОС и архитектуру;
- действия, после которых появляется проблема;
- ожидаемый и фактический результат;
- точный текст ошибки или обезличенный скриншот;
- для проблем записи — формат, качество, FPS, разрешение и состояние окна встречи.

Не публикуйте пароли, cookies, профиль Chromium, базу календаря, личные ссылки
на встречи или записи лекций. Перед отправкой журнала и скриншота скройте
имена, адреса и другие личные данные. Для воспроизведения достаточно
демонстрационных данных.

## Если есть идея

Создайте [Issue](https://github.com/tatpow/telecon/issues/new) и опишите задачу,
которую хотите решить: что неудобно сейчас и какой результат нужен.
Для заметного изменения поведения или дизайна сначала полезно обсудить идею,
чтобы не тратить время на несовместимые решения.

Небольшие исправления ошибок, опечаток и документации можно сразу присылать PR.

## Первый pull request

1. Сделайте fork и отдельную ветку.
2. Прочитайте [AGENTS.md](AGENTS.md): там описаны границы приложения,
   работа с видеофайлами и требования к проверкам.
3. Подготовьте окружение по [BUILDING.md](BUILDING.md). Для релизных сборок
   используется CPython 3.12.
4. Внесите одно понятное изменение. Не добавляйте профили, cookies, базы,
   пользовательские видео, виртуальное окружение или готовые сборки в Git.
5. Запустите проверки и опишите результат в PR.

Из каталога проекта:

```text
python -m unittest discover -s tests -v
node --check ui/app.js
node --check ui/motion.js
python tests/check_ui.py
```

Для UI приложите скриншот до/после на демонстрационных данных.
Для исправления поведения добавьте тест, который воспроизводит проблему,
когда это помогает предотвратить её повторение. Одних тестов, повторяющих
строки реализации, недостаточно.

Нативные изменения проверяйте на соответствующей ОС.
Unit-тесты и CI smoke-check не заменяют проверку записи на Windows 11.
Ограничения конкретного тестирования укажите прямо: «macOS не проверял» —
полезнее, чем предположение, что всё должно работать.

## Если помогает ИИ

Использовать ИИ для кода, тестов, документации и анализа можно.
В PR кратко отметьте, где он помог, что вы проверили сами и какие ограничения
остались. Не нужно прикладывать полную историю запросов или личные переписки.

Вы отвечаете за присланное изменение: прочитайте diff, проверьте зависимости
и лицензии, удалите выдуманные утверждения и запустите указанные проверки.
Не отправляйте ИИ личные данные пользователей или секреты.

Проект сохраняет обозначение **vibecode / GVP** в смысле
[Generated Viable Product](https://github.com/tatpow/GVP).
Участие ИИ не освобождает от проверки результата.

## Что написать в описании PR

Коротко объясните проблему, новое поведение и способ проверки.
Если затронуты файлы, данные или поддержка платформ, укажите это отдельно.
Большую задачу лучше разделить на несколько понятных изменений.

GitHub Actions проверяет PR на Linux, Windows и macOS. Workflow не использует
`pull_request_target`, не публикует релиз и не получает секреты для тестов PR.
Нативные сборки запускаются отдельно вручную.
Изменения workflow также проверяйте статически и просматривайте их diff.

Отправляя вклад, вы соглашаетесь распространять его на условиях
[лицензии проекта AGPL-3.0](LICENSE).
